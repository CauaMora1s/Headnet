# Key management

Where every secret in Headnet lives, who can read it, and what happens when it
leaks.

**Status: mostly planned.** Key generation and storage arrive with the client
daemon in [Phase 2](../ROADMAP.md#phase-2--client-mvp). This document records
the design the implementation must satisfy, and marks what exists today.

---

## The rule everything else follows

> **A private key is generated on the device that will use it, and never
> leaves that device.**

Not "is encrypted in transit". Not "is only sent over TLS". Never sent.

There is no API endpoint that accepts a private key, no configuration field
that holds one, and no diagnostic that prints one. When the daemon is built,
a test will assert that no serialised request contains private key material.

The consequence is the property that makes the whole design defensible: an
attacker who takes the control-plane server, or its database, or its backups,
gains no ability to decrypt any traffic — past or present. There is nothing
there to steal.

## The key material

| Secret | Generated by | Stored where | Leaves the device? |
| --- | --- | --- | --- |
| **WireGuard private key** | Client daemon | Device, 0600, root-owned dir | **Never** |
| **WireGuard public key** | Derived from the private key | Device, and the server | Yes, by design |
| **Session cookie** | Server | Browser (`HttpOnly`) and server | Server ↔ browser only |
| **Setup key** | Server | Shown once; stored hashed | Yes, to the enrolling user |
| **Password** | User | Never stored — only an Argon2id hash | No |
| **OIDC client secret** | Identity provider | Server config, via environment | No |
| **Database DSN** | Operator | Server config, via environment | No |
| **Relay token** | Server | Client memory, short-lived | Client ↔ relay |
| **TLS private key** | Operator or ACME | Reverse proxy, usually | No |

## WireGuard keys

### Generation

Curve25519, from the platform CSPRNG (`crypto/rand`). The daemon generates the
key at enrolment; the server sees only the public half.

Headnet implements none of this cryptography itself. WireGuard's key handling
is used as WireGuard defines it. See
[ADR-0002](../architecture/decisions/ADR-0002-use-wireguard.md).

### Storage (Phase 2)

| Platform | Path | Protection |
| --- | --- | --- |
| Linux | `/var/lib/headnet/device.key` | 0600, owned by the daemon user, in a 0700 directory |
| macOS | `/var/lib/headnet/device.key` | Same; Keychain under evaluation |
| Windows | `%ProgramData%\Headnet\device.key` | ACL restricted to SYSTEM and Administrators |
| Android | Android Keystore | Hardware-backed where available |
| iOS | Keychain, `kSecAttrAccessibleAfterFirstUnlock` | Secure Enclave where available |

Two rules the implementation must hold to:

- **Permissions are verified on read, not just set on write.** A key file that
  has become world-readable is a compromised key, and the daemon must refuse
  to start rather than continue with it.
- **The key never enters a log, a diagnostic bundle or an error message.**

### Rotation (Phase 11)

Rotation generates a new key locally, registers the new public key, waits for
peers to converge, and only then discards the old one. The order matters: the
reverse would disconnect the device from a network it then cannot reach to
complete the rotation.

Rotation will be available on demand and on a schedule, and is the correct
response to a suspected device compromise — alongside revocation.

### Loss and revocation

Losing a private key is not a disaster: the device re-enrols and gets a new
one. Revoke the old device record so its public key stops being distributed.

Revocation must *disconnect*, not merely delist. A device removed from a list
whose peers still hold its configuration is still on the network. See
[Phase 3](../ROADMAP.md#phase-3--device-to-device-networking).

## Setup keys

A setup key enrols a device without an interactive login — for a headless
server, a container, or a machine being provisioned:

```bash
headnet up --setup-key <KEY>
```

That makes it a credential, and it is treated as one.

**Implemented:**

- **Displayed once.** The server stores only a SHA-256 hash, so a database read
  yields nothing usable. A short display hint is kept so a key can be
  recognised in a list without being spendable.
- **Revocable**, immediately. Revoking twice keeps the first timestamp — when
  the key actually stopped working.
- **Expiring by default**, after seven days. A key with no expiry requires an
  explicit `never_expires`.
- **Optionally single-use.** The use count is checked in the `UPDATE`'s `WHERE`
  clause rather than read and then compared, so two enrolments racing for the
  last use of a key cannot both win.
- **Audited.** Creation, every redemption with its source address, and
  revocation.
- **Issuing is administrative.** A setup key mints a credential that puts a
  machine on the network.

**Not yet enforced:** a key's **scope** (its tags) is stored and returned but
nothing acts on it. Phase 6's policy engine will. Until then a key grants what
its creator could grant, and this is stated rather than implied.

**Operationally:** treat one like a password. Do not commit it, do not paste
it into a chat, do not leave it in shell history. Prefer short-lived
single-use keys for provisioning; prefer a scoped, expiring key over a
long-lived one for a fleet.

If one leaks: revoke it, then audit what enrolled with it.

## Passwords

**Implemented.** Only relevant when the `local` authentication provider is
enabled.

- **Argon2id**, with parameters from current OWASP guidance.
- **Per-password salt** from `crypto/rand`.
- **Parameters stored alongside the hash**, so they can be raised later
  without invalidating existing passwords.
- **Constant-time comparison.**
- **Plaintext never stored, never logged, never returned by any API.**

Headnet will not implement its own password hashing beyond calling
`golang.org/x/crypto/argon2`.

## Server-side secrets

The control plane holds two secrets of its own: the database DSN, and any OIDC
client secret.

**Supply them through the environment, not the configuration file.** The YAML
file is meant to be committable to your own configuration management; the
environment is not. `.env.example` documents every variable, with placeholders
rather than values.

Anywhere Headnet renders its configuration — start-up logging,
`headnet-server -print-config` — it goes through `config.Redact`, which masks
every field tagged `secret:"true"`. **This is implemented and tested today.**

A populated secret renders as `***`; an *unset* one renders as empty. That
distinction is deliberate: the most common configuration mistake is failing to
supply a secret at all, and an operator reading a redacted dump has to be able
to tell "it is set, I cannot see it" from "it is missing".

## Backups

Backing up the control plane means backing up the database. It contains:

- User accounts and Argon2id password hashes
- Device records and public keys
- Setup key hashes
- Policy and address allocations

**It contains no private keys**, so a stolen backup does not yield the ability
to decrypt traffic. It does yield the complete shape of the network, and the
password hashes are worth attacking offline.

Therefore:

- Encrypt backups at rest.
- Restrict who can read them as tightly as the live database.
- Test restoring, before you need to.

Note that a restored backup on a fresh database produces a **new instance
ID**, which clients that pinned the old one will notice and refuse. That is
intended: it is the signal that distinguishes "my server came back" from "an
impostor is answering at my server's address". Restoring the database file
itself preserves the ID.

Full procedure: [docs/deployment.md](../deployment.md).

## For contributors

If you are writing code that touches key material:

1. **Never** put a private key, password, token or setup key into a log call,
   an error message, a metric label, or an API response.
2. Use `config.Redact` for anything that renders configuration.
3. When adding a configuration field that holds a secret, tag it
   `secret:"true"` — and add a test asserting the value does not survive
   redaction.
4. Reduce secrets to non-reversible references — an ID, or a fingerprint —
   before they go anywhere observable.
5. Read the [threat model](threat-model.md) first.
